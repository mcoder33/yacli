# Повторы и переносы календарных событий

Эта доработка форка добавляет `calendar update` (псевдоним `calendar move`)
и MCP-инструмент `yacli.calendar.update`. Установочные скрипты и автоматическое
обновление в остальной документации по-прежнему относятся к upstream.
Для проверки этой ветки используйте отдельную локальную сборку.

## Выдача за период

`calendar events` запрашивает серверное раскрытие повторов через CalDAV
`calendar-data/expand`. RRULE, EXDATE, RDATE, перенесённые исключения и отмены
раскрывает сервер, а клиент проверяет ответ, убирает отменённые и исторические
компоненты, сортирует по времени и только затем применяет `--limit`.

Окно полуоткрытое `[from, to)`: событие попадает в него при пересечении
интервалов. Мгновенное событие включается, если его начало находится в окне.
Даты без времени обозначают UTC-полуночь; события на весь день сравниваются
по оси календарных дат с UTC-полуночью и исключительным концом. Для выборки
полных дней используйте границы `YYYY-MM-DD`. Привязка событий на весь день
к часовому поясу календаря при произвольных почасовых границах не реализована.

Ответ содержит исходный `recurrence_id` экземпляра, нормализованный в UTC
(либо `YYYY-MM-DD` для события на весь день). В CLI JSON прежний ключ `id`
сохранён, а `recurrence_id` добавлен; в MCP UID называется `uid`.
В табличном выводе появился столбец `RECURRENCE_ID`.
Сервер вправе не вернуть RECURRENCE-ID первого экземпляра серии. Для его
переноса задайте `scope=occurrence` и исходное начало в `occurrence`;
клиент проверит экземпляр раскрытием серии перед записью.

Если сервер возвращает нераскрытые правила повторов или пропускает запрошенные
данные, команда завершается ошибкой вместо заведомо неполного расписания.
Локального движка повторений и скрытого перехода к старой выдаче нет.

## Предпросмотр и запись

Явно укажите профиль, календарь и область изменения. Примеры используют
синтетические идентификаторы; замените их значениями из вашей выдачи.

```sh
# Одиночное событие: длительность сохранится.
yacli calendar move example-event \
  --account example --calendar team --scope event \
  --start 2026-10-27T11:30:00+04:00 --dry-run

# Один экземпляр серии: occurrence — исходная дата, даже после переноса.
yacli calendar update example-series \
  --account example --calendar team --scope occurrence \
  --occurrence 2026-10-20T07:30:00Z \
  --start 2026-10-27T11:30:00+04:00 --dry-run

# Запись после просмотра: удалите --dry-run.
# При необходимости привяжите запись к ETag из before.etag:
yacli calendar move example-series \
  --account example --calendar team --scope occurrence \
  --occurrence 2026-10-20T07:30:00Z \
  --start 2026-10-27T11:30:00+04:00 --if-match '"reviewed-etag"'
```

Можно менять `--end`, `--summary`, `--description`, `--location`.
Пустое описание или место задаются пустой строкой. При отсутствии нового конца
сохраняется прежняя длительность; исходный DURATION сохраняет свою семантику
номинальных дней при переходе DST. Для интервалов с DTEND сохраняется прошедшее
время. События на весь день принимают даты, события со временем — RFC3339 с
явным смещением и целыми секундами. Преобразование между этими типами запрещено.

`scope=event` применим только к одиночной встрече. `scope=occurrence` требует
исходного RECURRENCE-ID. Новый экземпляр создаётся как исключение в исходном
объекте серии; мастер, другие исключения и исходный RECURRENCE-ID сохраняются.
Повторный перенос редактирует то же исключение.

MCP использует те же правила:

```json
{
  "name": "yacli.calendar.update",
  "arguments": {
    "account": "example",
    "calendar": "team",
    "uid": "example-series",
    "scope": "occurrence",
    "occurrence": "2026-10-20T07:30:00Z",
    "start": "2026-10-27T11:30:00+04:00",
    "dry_run": true
  }
}
```

Предпросмотр возвращает `account`, `calendar`, `scope`, `before`, `after`,
`write_outcome=not_written`. Он выполняет только чтения; PUT и уведомлений нет.
`after.etag` при предпросмотре относится к исходному объекту. Занятость других
участников и пересечения встреч эта версия не вычисляет.

## Защита записи и ограничения

Перед изменением выполняются UID-lookup и GET полного объекта с сильным ETag.
Для нового исключения дополнительно запрашивается раскрытие того же объекта
с проверкой ETag. Изменяется дерево iCalendar, включая неизвестные поля,
участников, VTIMEZONE, ссылки и VALARM. Полный результат сериализации проверяется
повторным разбором до PUT.

PUT отправляется один раз с `If-Match`; при наличии Schedule-Tag также передаётся
`If-Schedule-Tag-Match`. Ответ 412 означает конфликт, автоматической перезаписи
нет. После записи выполняется GET: проверяются целевые значения и сохранность
переданных компонентов и полей. Серверные revision metadata и SCHEDULE-STATUS
могут изменяться. Существенная нормализация других полей сервером может привести
к консервативному результату «не удалось подтвердить», даже если перенос выполнен.

При потере ответа или HTTP 5xx клиент читает объект и сверяет результат.
`verified_after_uncertain_response` означает подтверждение чтением без второй
записи. Если подтвердить результат нельзя, сначала перечитайте календарь;
ошибка не означает гарантированный откат. Обычный подтверждённый результат —
`write_outcome=verified`.

Уведомления остаются ответственностью CalDAV-сервера. Поле
`scheduling=server_managed_delivery_unverified` не подтверждает доставку почты
или принятие приглашения. Отдельные SMTP-приглашения клиент не отправляет.
Изменение встречи другого организатора запрещено: email организатора должен
совпадать с email профиля. Делегирование и алиасы организатора не поддержаны.

Другие явные ограничения: изменение всей серии, RANGE-исключения, floating
DATE-TIME, неизвестные/custom VTIMEZONE для преобразования времени. Известные
TZID обрабатываются через IANA-базу chrono-tz; неоднозначные локальные времена
возвращают ошибку. Автоматического изменения всей серии при ошибке нет.

CalDAV discovery и ресурсы должны находиться на настроенном origin. HTTP
redirects отключены, чтобы повторно не отправлять запись и учётные данные
по адресу, полученному из перенаправления. Имена календарей должны быть
однозначными; предпочтительны точные ID или href.

Основания протокола: [RFC 4791, expansion](https://www.rfc-editor.org/rfc/rfc4791#section-9.6.5),
[RFC 5545, recurrence identity](https://www.rfc-editor.org/rfc/rfc5545#section-3.8.4.4),
[RFC 6638, scheduling](https://www.rfc-editor.org/rfc/rfc6638).

## Сборка отдельно от установленной версии

Требуется Rust 1.88 или новее. Минимальная версия в Cargo.toml уточнена:
исходный код уже использовал let-chains; новая библиотека также требует 1.88.

```sh
cargo build --locked --release
./target/release/yacli calendar update --help
# Для существующих секретов в системном хранилище задайте backend явно:
YACLI_SECRET_BACKEND=keyring ./target/release/yacli calendar calendars --account example
```

Команды не заменяют установленный бинарник и не меняют MCP-конфигурацию.
В существующем профиле не нужно повторять login. Debug-сборка по умолчанию
использует file backend; для Keychain нужен явный `YACLI_SECRET_BACKEND=keyring`.

Для последующего переключения сначала сохраните копию установленного бинарника
и текущей MCP-записи, затем укажите абсолютный путь к новой сборке, сохранив
аргумент `mcp` и прежнюю переменную backend. Для отката верните прежний путь
и перезапустите подключение MCP. Изменять профили или экспортировать секреты
для переключения не требуется. Автообновление через `yacli update` по-прежнему
смотрит на upstream и может заменить форк; обновляйте эту ветку сборкой из исходников.

Проверки используют синтетические .ics, mock CalDAV и локальный TCP-сервер,
который сохраняет PUT и закрывает соединение до ответа. Живые записи в Яндекс,
доставку уведомлений и реальные пользовательские профили эти тесты не проверяют.
